# 当前架构决策

更新：2026-11-20。当前决策替代旧控制性架构文字；旧 ADR 快照位于 archive/2026-11-20/architecture-decisions.md。

## A01 产品壳与后台能力

前端按 Synthesia 截图和官方流程组织页面；前台只表达用户正在选曲、设置、看谱和弹奏需要的对象。DuET、音频处理、目录索引、转调量化、谱面准备和迁移作为应用服务运行。复杂算法、模型路径、任务回执和存储细节进入后台或按需设置。

## A02 目标依赖关系

```text
Screens / screen controllers
  → Application facade / typed queries and commands
    → SongRepository | PlaybackSession | ScoreService | JobService
      → Music domain + ports
        ← storage / filesystem / MIDI / audio / VST3 / model-process adapters
```

| 边界 | 拥有的内容 | 不应承担的内容 |
| --- | --- | --- |
| Music domain | 身份类型、时间轴、音符、手别、变换和谱面关系 | Tauri、设备句柄、文件对话框、窗口状态 |
| SongRepository | 歌曲/版本/位置/标注的事务、迁移、查询 | 播放时钟与前端组件 |
| PlaybackSession | 播放事实、事件游标、等待键、模式、seek/loop/stop | 全库扫描、制谱、磁盘写入和评分 |
| ScoreService | 解析、页/范围缓存、对齐、采用谱面 | 音频线程和业务导航 |
| JobService | 任务身份、进度、取消、超时、失败回执与旧结果拒绝 | 给每个任务增加常驻前台卡片 |
| Device adapters | MIDI 输入输出、SF2、Pianoteq、设备重连 | 歌曲归属、谱面选择或练习评分 |
| Desktop shell | 原生文件入口、窗口/生命周期、进程适配 | 音乐领域与重复业务存储 |
| Screen controllers | 导航、选择、用户编辑草稿、交互命令 | 逐帧时间推进、完整乐谱重算、路径身份判断 |

这些首先是模块边界。按依赖需求抽 crate；不为目录数量建立新微服务或重复 DTO 层。

## A03 存储目标

中心目录使用 SQLite/rusqlite，由专用存储服务写入。统一歌曲关系、资产位置、版本、手别和派生任务；大文件按内容哈希放在独立资产库。数据库原子提交与文件提交日志配合：先写临时资产、核对哈希并持久化，再提交引用；失败留下可回收临时文件，不提交空引用。数据库与外部文件不是同一个原子事务，不能仅凭 SQLite 事务宣称两者同时提交。

SQLite 依据其[原子提交说明](https://www.sqlite.org/atomiccommit.html)处理关系记录；Rust 接入使用 [rusqlite](https://docs.rs/rusqlite/latest/rusqlite/)。实施时选择与当前工具链兼容的固定版本及锁文件。B01 已接入歌曲关系目录、MIDI 副本和按内容保存的 JSON 标注文档。普通文件演奏由新文档拥有手别和指法；workspace、会话设置及非文件演奏入口仍有过渡消费者，完整统一存储尚未完成。依赖锁文件中的 thiserror 升级由 rusqlite 的跨目标传递依赖要求触发。

迁移生成新目录、迁移清单和校验结果。切换后只写新存储；旧适配器提供只读导入和导出恢复。兼容不意味着同时维护两套活动核心。

## A04 音乐与实时路径

原始 MIDI 字节的 BLAKE3 身份与文件路径分离。tick 是音乐顺序的基础；tempo map 决定秒，小节由 meter map 决定；播放 BPM 是时间尺度，不改写源文件。手别和播放职责独立，等待模式只跟踪所需琴键，不计算准确率或达标。

播放载荷预先编译为不可变事件序列，切换载荷使用版本标记和有界消息。音频回调避免 I/O、分配和阻塞锁。目录、解析、模型和存储工作在后台执行；停止与止音命令有独立响应路径。

## A05 渲染与谱面

屏幕读取时间锚点推算显示时刻，音频/引擎拥有事实时钟；React 处理低频状态。瀑布通过索引查询可见区间，按可见数据绘制；不逐帧遍历全曲、序列化全谱或重建 React 树。谱面页和节拍索引由后台生成，页/范围缓存有大小上限。高级皮肤和特效通过相同渲染设置访问，不新增默认工作区。

## A06 原创替换

Neothesia 应用逻辑逐模块退出：先稳定领域协议，再以功能规格和独立实现替换消费者。已有 GPL 代码在退出前准确保留来源。midly、cpal、midir、rtrb、oxisynth、Verovio、PDF.js、SQLite 等通用依赖单独记录来源和许可；原创应用层不要求自研操作系统、标准格式解析库或音频驱动。

审计已见代码不能称为严格 clean-room 独立隔离开发。后续实现应记录真实开发来源，不作无法证明的隔离声明。最终许可结论依据实际保留内容、集成方式及来源审核。

## A07 迁移方式与退出条件

每批完成“新实现 → 消费者接入 → 必要检查 → 旧路径退出”。适配层有明确任务编号和移除条件，禁止无限保留双写/双 UI。App.tsx 退为装配和路由；Player 聚合退为应用服务协调，评分的旧可变处理器退出主线运行和写入路径，旧历史可通过独立导入兼容读取。

## A08 交付与变更范围

当前支持 Windows 桌面正式包；浏览器入口服务开发调试。旧原生跨平台、视频编码 CLI 和原 AI wrapper 不属于当前产品入口。已有九项未提交曲库调整属于本轮之前内容，独立保留。文档不能把旧版本检查、源码存在或局部截图等同于当前产品完成。

## A09 文件演奏标注与会话配置

手别与播放职责分开：SongAnnotation 文档保存轨道/逐音手别、指法、小节和谱面关联；SessionSettings 保存自动/自己弹/静音、可见性与练习方式。迁入新文件演奏后清空旧 parts，避免两处活动写入。标注文档是由 SongRepository 绑定内容身份的文件资产，经既有提交日志与设置一起发布；SQLite 不重复保存一份可独立修改的相同负载。

当前 core/library 提供旧接口的窄路由：只有完整 library/assets/midi 或 library/assets/exercises 的受管理布局会进入新文档适配器，外部文件不会仅因名字是哈希而匹配。内置模板、生成练习和曲目包已接入，旧元数据与位置兼容入口仍需收束；旧 core 的来源替换任务继续执行。轨道编辑从普通命令和演奏调节入口统一进入后台事务，避免新持久化操作落在播放线程。

## A10 持有谱面与可移植演奏

MIDI 与 MusicXML 按内容保存不可变字节，关系文档和用户命名可单独更新。原路径丢失时按内容恢复到已持有资产；占用资产内容变化时保留该文件并另存完整副本。启动恢复和生成练习的迁移在准备工作线程完成，运行时接收已读资产和观察记录。

曲目包第 19 版将原始 MIDI 和练习变换分开保存，恢复后可返回原调与原始时值。旧格式经版本检查导入。新导入在提交文件事务后登记中心曲库；登记失败只生成一条后台待恢复提示，已保存的演奏继续可用。完整歌曲使用 panthesia-song 外层归档组合全部演奏包。它复用单演奏的校验与恢复，单次提交文件，再经持久回执发布歌曲关系；关系发布由 song_repository/archive 模块负责，重启后可幂等继续。不同演奏的谱面身份和校对决定通过稳定身份与恢复版本关联，刷新目录后继续有效。
