# 现代化改造与功能补齐

更新：2026-11-19。用户授权长期进行架构优化、必要重构与 Synthesia 官方功能补齐。本计划为当前开发主线；此前日常版与 R1 / R2 清单保留各自交付含义。

## 产品结果

用户能够完成“选曲 → 配置声部与音源 → 分手练习 → 看谱或瀑布演奏 → 分段反复 → 保存并回顾”，并有独立自由演奏和多轨录音工作区。界面保持简体中文，视觉质量、皮肤与琴键特效作为持续要求。

功能范围见 [官方对照矩阵](synthesia-feature-matrix.md)。实现官方软件公开能力时采用 Panthesia 自己的设计、数据模型与交互表达。依赖设备、其他平台、在线服务和授权内容的项目仍留在总表，单独安排适配和验收。Windows 本地练琴优先交付。

## 模块职责与依赖

```text
中文界面：曲库 / 演奏 / 回顾 / 自由演奏 / 设置
          ↓ 命令与只读数据契约
应用服务：用例编排、异步准备、取消与结果提交
          ↓                          ↓
音乐领域：歌曲、拍位、练习、录音      端口：存储、设备、外部工具
          ↑                          ↑
只读投影：谱面与瀑布                适配：文件 / MIDI / SF2 / VST3
```

约束：

1. 音乐领域不导入 React、Tauri、HTTP、设备或文件对话框。
2. 音频回调不做文件访问、解析、界面通知和无界任务；保留现有无阻塞消息队列。
3. 播放调度只处理短命令、MIDI 输入、已准备结果和状态发布；重工作在后台，提交前核对来源身份。
4. 瀑布显示时钟只推算显示位置；播放位置、评分、等音和循环边界仍由引擎决定。
5. 数据契约不引用组件；显示格式函数不初始化网络或桌面传输。
6. 设置和历史归属对应领域服务；源 MIDI / 原谱、演奏版本、练习变换与显示配置分开保存。
7. 领域之间交换明确数据或应用服务调用，避免相互读取私有字段。旧 Player 在迁移期仍有耦合，逐批收窄，不能把拆文件当作解耦完成。
8. 新接口只为当前真实用例建立；重复调用规则稳定后再抽象。不为目录统一改动旧原生入口或引入整套框架。

## 架构完成标准

- 可单独理解和修改曲库、练习、录音、设备、谱面与显示模块，公共接口含明确身份和生命周期。
- 核心公共契约有一个声明来源；前后端仍有手写投影时明确记录，逐批迁移到生成契约。
- 公共类型与纯算法不依赖界面；界面模块通过功能服务操作业务。
- 高频状态按订阅范围发布，工具页面不因每帧位置变化重绘；静态资源与渲染缓存有上限和失效条件。
- 暂停、跳转、循环、换曲、设备断开与退出均能结束旧状态，过期结果不能污染新会话。
- 用户源资料保留；迁移有版本检查、可恢复旧数据和明确失败反馈。

文件行数用于发现问题，不作为验收指标。架构质量通过依赖方向、职责归属、修改影响范围与具体工作流判断。

## 检查与交付节奏

每批执行受影响项目的构建，以及直接覆盖风险的现有关键检查。纯结构变更以类型 / 编译和已有行为检查为主；用户行为变更补一个真实工作流。渲染变更才复核对应瀑布场景；音源变更才重新录制声音证据。资料迁移使用隔离副本。达到批次条件后进入下一批，里程碑统一打包。

当前长期任务保持进行中。阶段报告须分别写明“本批完成”“仍待实现”“当前可运行版本”，不得用局部完成替代全工程完成。
