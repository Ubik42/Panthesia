## 原库与本机实现的关系

内置 SoundFont 合成仍使用 OxiSynth 0.1.0，设备输出使用 CPAL 0.18。原项目 `panthesia/src/output_manager/synth_backend.rs` 也采用该组合；本机桌面版的音频接入位于 `panthesia-engine/src/audio.rs`，播放调度、练习评分、线程和存储边界有后续实现。原库不是本机全部行为的来源。

Pianoteq 6 的合成算法由插件提供，经 vst3-host 0.9.0 输出。Microsoft GS Wavetable Synth 由 Windows 提供，应用发送 MIDI。三个独立合成路径都卡顿时，应同时检查共用调度和前端，不能直接把故障归于 OxiSynth。

## 本批改动

1. 内置音源的 MIDI 队列从标准同步通道改为 rtrb 的 SPSC 环形队列。生产者侧锁只用于串行化发送；音频回调不获取这把锁。保留代际校验、溢出止音和过期消息处理。
2. 队列、止音和节拍器控制按 64 帧边界处理；音量和峰值按音频块处理。原接入层对每个采样执行这些操作，产生大量重复工作。正常回调使用预先分配的转换缓冲。
3. 启用 CPAL 的 realtime 特性，在支持的平台申请音频线程优先级。它不等同于已保证所有硬件无欠载。
4. 输出电平与插件反馈读取从约 1 ms 一次降至约 16 ms 一次，减少控制线程轮询和插件电平快照分配。
5. 琴键底图只在尺寸、显示设置或音域改变时重建。每帧仅重绘活动键、等待键及受白键覆盖影响的相邻黑键，保留材质、反光与特效。
6. 五线谱与纸谱页不再挂载被覆盖的瀑布画布。MIDI 五线谱缓存静态音符组件，只有相关高亮或音符变化时更新。
7. 加入播放调度与内置音频回调耗时记录，入口为“设备与声音 → 播放性能记录”。这些高频指标属于局部读数，不参与应用外壳状态，避免诊断本身触发整页重绘。

性能记录中，`maxGapMs` 表示播放循环最大间隔；`maxTickMs`、`maxPublishMs` 分别表示音乐处理和状态发布的最大耗时。音频回调的 `maxRenderUs` 是整块生成耗时，`overBudgetCallbacks` 是计算时间超过该块音频长度的次数。它不等同于完整的硬件欠载统计，也不覆盖操作系统全部 DPC 延迟。

## 成熟实现参考与选择

| 参考 | 本次用途与结论 |
| --- | --- |
| [PortAudio 回调规范](https://portaudio.com/docs/v19-doxydocs/writing_a_callback.html) | 回调须按时完成，避免分配、文件访问和可能阻塞的锁；用于审查线程边界 |
| [miniaudio](https://miniaud.io/docs/manual/index.html) | 参考设备回调、缓冲和无锁环形缓冲结构；它属于输出/混音层，不能代替钢琴合成器本身 |
| [rtrb](https://github.com/mgeier/rtrb) | 明确面向实时音频的 SPSC 队列；已用于内置音源消息传递 |
| [FluidSynth](https://www.fluidsynth.org/api/settings_synth.html) | 成熟 C 合成器路线，提供合成多核设置和实时相关选项；本批未在本机完成其同条件速度对照 |
| [RustySynth](https://github.com/sinshu/rustysynth) | 纯 Rust 的 SoundFont 替代候选；已进行本机离线合成对照，本组场景没有速度优势 |
| [OxiSynth](https://github.com/PolyMeilex/OxiSynth) | 原项目使用的合成器，受 FluidSynth 启发；本批保留合成核心，改接入方式 |

可重复的合成对照入口：`cargo run --release --manifest-path tools/audio-benchmark/Cargo.toml -- default.sf2`。该独立工具不改变生产依赖或曲库。

同一 SF2、48 kHz、128 复音上限，重复 480 帧块，生成 10 秒音频，排除音色读取与初始化时间。本机一次 Release 结果：

| 合成器 | 8 个同时发声音符 | 64 个同时发声音符 |
| --- | ---: | ---: |
| OxiSynth 0.1.0 | 45.11 ms | 274.85 ms |
| RustySynth 1.3.8 | 63.24 ms | 285.05 ms |

这些数字是离线场景的计算时间，不是按键延迟，也不是所有音色或硬件上的排名。两库默认增益、效果和输出波形不同，本批未作音色等价或听感评判。空队列微基准另外记录了轮询次数变化，其比值不能当作整个音频系统的提速倍数。

## 实际播放记录

原始记录位于 `work/performance-20261118/`。检查使用独立资料目录，没有改写用户正式资料。

运行时采样采用本机开发服务和开发前端，用于定位调度与重复绘制；它不是前后两份正式包的完整速度对照。离线合成库对照单独使用 Release 优化构建。

- `profile.json` 保留中间的 A/B 采样。该轮带临时诊断字段，包含尚未完成隔离的外壳重绘开销，不能当作此前发布包的完整性能基线。
- `profile-final.json` 为完成字段隔离后的最终采样：1920×1080，Look at the Sky，演出光效、流星样式、十六分网格。每个场景连续 10 秒，三个音源分别运行；另外采样五线谱页。
- 瀑布的绘制回调中位数约 0.60 ms，95 分位约 1.00–1.10 ms。五线谱页隐藏画布绘制次数为 0。
- 内置音频块最大 1056 帧；记录到的最大计算耗时 1.278 ms，按实际音频块时限统计的计算超时为 0。
- 本轮各阶段累计播放调度最大间隔 7.944 ms，没有超过 20 ms 的播放循环间隔，声音事件迟到计数为 0。
- Pianoteq 场景仍有一次 78.3 ms 的画布回调间隔，播放线程同时没有相应迟到。该记录说明视觉端仍可能出现短时掉帧，不能宣称整机所有卡顿已经排除。
- `audio-check.json` 为三条实际输出路径的回录：内置 RMS 0.02029、Windows MIDI 0.02510、Pianoteq 0.08000。输入关闭，连续播放自动发声。

本轮未稳定复现用户描述的画面和声音同时长时间停顿。已处理代码中确认的重复工作，并提供用于区分调度与合成耗时的记录。短样本不构成长期无卡顿保证；本批没有把换库名称当作问题已解决的证明。
